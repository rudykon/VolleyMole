# 四球自动化可复现性核验 · 2026-09-20

> 文中 `runs/`、`outputs/` 路径指项目根目录下的本地实验产物，未随源码发布到 GitHub。

**这四球的剪辑不依赖手工时间点，可由代码和已有 API 回答自动生成；当前还不是已经验证完成的“新录像输入 → 一键成片”生产流程。** 用户现已确认四球的观看效果满足需求。本次记录这项观感验收，不改变历史原始回答，也不把模型动作和结果描述的错误改写为正确。

本轮只做离线核对，没有新增 API 调用或读取密钥。

| 四球动作焦点 | 都来自自动模型缓存；对应全回合扫描请求、候选、源视频与时间范围均校验一致 | 四个测试回合由实验范围指定，未重新证明新录像最佳候选选择 |

核验还发现四项尚未统一的实现差异：

1. **请求配置不统一。** 四个有效展示结果来自三组生成配置；此前连接失败、格式失败后的诊断修复由助手分步处理。不能把这段实验过程说成同一固定配置的一次批量运行。
2. **原生 Gemini 接口只在实验脚本里。** 正式请求代码仍走兼容的 `chat/completions`，尚未接入本轮原生流式请求配置。
3. **实验片与正式流程的剪辑规则不同。** 实验片直接使用模型 lead/tail；正式流程会增加已观察到的前后余量，并继续检查动作、边界和其他候选。因此接回正式入口时，即便回答相同，也未必得到完全相同的片段。
4. **一球存在格式例外。** 9.8 第 3 球返回单元素数组，实验导出读取其中的对象展示原始时间点，正式解码器会拒绝。离线试验发现，即使只去除外层数组，仍有模型自己声明开头、结尾处于运动中的规则冲突；单改 JSON 格式不能直接完成生产接入。

将原回答交给当前局部复核函数及轨迹检查后，9.15 第 2 球、9.8 第 1 球可通过该局部检查；9.15 第 8 球仍被要求补看开头；9.8 第 3 球在格式校验处停止。**这不是正式端到端通过率**：没有重新跑候选竞争、跨阶段判断、生产缓存绑定和新模型请求。

用户的反馈明确了本次四球的观看效果可以接受。此前自动验收还要求动作类别、后续触球与结果描述准确，部分要求超出了用户对这版回放的观感判断。后续应分别记录“成片观感”和“事件描述准确度”，并用这四球作为用户认可的回归样例；不能据此把不同录像、不同机位全部视为通过。

要完成一键接入，需要固定一组可运行的 API 配置，将现有自动候选选择、格式处理和实验片剪辑方式统一接入正式流程，再从新录像完整跑一遍并检查成片。各步骤已有实现基础，本轮没有证明新的模型调用必定返回相同答案，也没有宣称已经完成这项接入。
