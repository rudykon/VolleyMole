# 推理与成片性能优化

## 使用

```bash
.venv/bin/volleymole run --video data/样例视频/1.mp4 --top-k 5 --ranker rules \
  --devices cuda:0,cuda:1,cuda:2,cuda:3 --pipeline-depth 2 \
  --auxiliary-device cuda:0 --vball-engine ort-bound \
  --preview-workers 2 --render-workers 2 \
  --no-analysis-cache --output runs/optimization/example
```

推理调度与后端开关进入分析缓存指纹；调整设备或后端不会误复用另一配置的缓存。
`--no-analysis-cache` 用于新鲜推理测速，日常重复制作可去掉。

## 六项实现

1. **细分计时**：共享推理的 `analytics/summary.json` → `performance` 记录解码、BGR 转换、模型加载、消费等待、结果转换/写盘和各模型阶段。YOLO 另记录库自带的预处理（含传输）、推理、后处理计时；状态模型记录上传/类型转换；绑定后端记录上传、执行、下载。`gpu_execution` 记录工作队列等待。时间存在包含、重叠关系，不能相加当作命令总时长；尚未隔离的传输明确包含在所属阶段，不能当成纯 GPU 内核时间。
2. **按需预览**：默认 `--preview-scope needed`。规则模式用相同的纯规则选择函数预先确定入选回合，只为它们生成三张预览，再执行原有严格排名验证；API 模式为实际 shortlist 生成预览。五佳规则模式从 624 张减至 15 张。`--preview-scope all` 恢复完整候选预览。`--preview-workers 1..4` 控制并发，默认 2；抽帧命令和 JPEG 参数不变。
3. **跨批流水线**：`--pipeline-depth 2` 允许两个批次在途，并由单独的解码线程最多预取一批。每个时序模型只有一个工作线程，90 帧外部批次、30 帧状态窗口、9 帧球轨迹窗口、短尾和历史状态均保留。结果按源帧顺序汇合，主线程写盘期间 GPU 可继续下一批。默认深度 1，便于原调度对照。缓存批次会增加主内存占用，建议先用 2，最大 4。
4. **辅助检测分卡**：`--auxiliary-device cuda:0` 将辅助球模型迁到状态卡。辅助任务依赖同批球轨迹及动作结果，触发条件不变。缺省仍使用轨迹卡；是否加速取决于辅助帧比例与实际负载。
5. **推理后端**：`--vball-engine ort-bound` 使用现有 ONNX Runtime CUDA Provider，固定复用 FP32 输入/输出显存，通过 I/O Binding 执行原图；不降低输入分辨率、不量化、保留 CPU 热图及半径后处理。缺省 `ort` 保留原后端。绑定方式并非 TensorRT 编译引擎；当前环境没有 TensorRT Python 包，此次未引入 TensorRT 或 INT8。引擎收益应实测，不保证优于原后端。
6. **渲染并行**：`--render-workers 2` 并行生成独立完整回合，按倒计时顺序收集。依赖上一片段画面的转场和最终合成仍按依赖顺序执行。保留原 x264 preset、CRF、帧率、分辨率和音频参数；每个编码进程仍限制 4 个线程。默认 1，最多 4，避免高并发导致 CPU 超额竞争。

## 对照方法

```bash
# 四项推理对照顺序执行，避免同机互相竞争；保留 2 帧短尾。
.venv/bin/python scripts/benchmark_optimizations.py --video data/样例视频/1.mp4 \
  --output runs/optimization/my-ablation --max-frames 1802

# 在同一剪辑清单上比较单任务/双任务渲染；输出到新目录。
.venv/bin/python scripts/benchmark_render.py \
  --reference runs/four-gpu/timing-full-run-20260910 --output runs/optimization/my-render

# 全场原始证据、回合、选球、预览、片段和最终 MP4 对照。
.venv/bin/python scripts/compare_optimized_run.py \
  --reference runs/four-gpu/timing-full-run-20260910 --candidate runs/optimization/full-optimized
```

脚本拒绝覆盖已有基准目录，结果写入各运行目录的 JSON。新鲜推理不能由手工修改缓存完成状态代替。
没有减少全场帧数、模型输入尺寸或关闭最终音画/标题验证。单次测速受系统负载和模型热身影响，短测不代表全场倍数。

## 2026-09-10 实测结果

四张 RTX 3090，同源 `data/样例视频/1.mp4`（1915.235 秒、57531 帧），规则五佳，完整成片 170.5 秒。
本次一次连续运行总耗时 **638.290 秒（10 分 38 秒）**，没有复用分析缓存；输出目录 `runs/optimization/full-optimized`。

| 本次阶段 | 墙钟秒数 |
| --- | ---: |
| 输入准备与其他编排开销 | 8.294 |
| 共享分析：启动、推理、校验及证据复制 | 463.894 |
| 回合生成 | 12.606 |
| 所需 15 张预览 | 1.515 |
| 规则排名 | 0.005 |
| 双任务活力版渲染 | 109.873 |
| 全量解码、音画和标题验证 | 42.103 |
| 总计 | 638.290 |

分析阶段内的推理主体是 **450.291 秒**，包含模型加载；与前次主体 613.875 秒相比减少约 **26.6%**。
前次预览 624 张耗时 101.013 秒；本次仅生成需要的 15 张，用时 1.515 秒，图像内容一致。
前次因中断分两段测得的工作时间合计 908.321 秒，仅作历史参考：本次比该合计少约 29.7%，不是同一时刻、独占机器上的连续基准对照。

### 一致性与计时解释

- 74 项自动测试通过，覆盖原回归、短尾/历史顺序、并发异常传播、预览范围与缓存指纹。
- 整场检测 JSONL、球 CSV、PTS、球员索引、状态窗口、调用计数、回合清单、五佳选择及所需预览均与历史基线一致。
- 本次优化前的仓库已有片头去重标题修复（提交 `69f3bd0`）。历史成片的五段快切和首个转场因呈现代码版本不同而不适合做字节基线；该差异保留在 `optimization_comparison.json`，没有掩盖。
- 使用当前代码串行渲染作画面基线，本次完整优化成片的所有片段与最终 MP4 均逐字节一致；完整审计在 `runs/optimization/full-optimized/optimization_comparison_rebased.json`。
- 不以总计时中的 463.894 秒与历史的 613.875 秒直接相除，二者范围不同。主体对主体应比较 450.291 与 613.875 秒。
- 流水线中的解码 105.209 秒、BGR 转换 116.099 秒与模型工作重叠；解码消费者实际等待仅 0.857 秒。人物线程任务累计约 444.114 秒，已接近推理主体墙钟时间。球轨迹的 CPU 后处理/半径计算累计约 256.504 秒，绑定图执行约 20.786 秒，说明后续不能只围绕 GPU 图执行优化。
