# 慢回放选点与完整性

慢回放需要同时选对动作、保留完整过程。普通二传、球在空中到达最高点、球员落地，都不能单独证明出现了精彩扣球或救球已经完成。复核在入选回合排名完成后、渲染前运行，保留原有完整回合和模板，以原速的 2/3 播放通过核验的动作序列。

正常回合、片头快切和慢回放统一采用单画面：跟球视角铺满竖屏，不叠加底部全场小窗、分割线或回放边框。保留源画面高度，按竖屏比例平滑跟球裁切；无有效轨迹时采用居中单画面。默认不追加全场镜头；需要交代站位时，全场只能作为单独的回放镜头出现。更改构图不改变入选回合及回放首尾，也不触发新的模型调用。

渲染记录保存逐帧裁切位置，画面验收直接与原片对应裁切比较，检查范围覆盖画面下半部；无需靠常驻全场小窗验证对齐。旧分屏文件仍可按旧记录校验。

## 用法

```bash
# 新比赛：所有入选回合都有合格慢回放后才生成成片
.venv/bin/python -m volleymole match --input-dir data/样例视频 --date 2026.9.8 \
  --design-suite matchday --replay-review required

# 已有剪辑单：复核慢回放，不改选球、排名和完整回合区间
.venv/bin/python -m volleymole review-replays --run runs/你的运行目录

# 复核通过后重新渲染与技术验收
.venv/bin/python -m volleymole.media_worker render --run runs/你的运行目录 --style lively
.venv/bin/python -m volleymole verify --run runs/你的运行目录 --style lively
```

先在项目的 `llm_api.json` 或环境变量中配置视觉模型。`review-replays` 默认使用 `required`；常规 `run` / `match` 默认使用 `auto`。`--stop-after replay` 可只运行到复核完成。

| 模式 | 行为 |
| --- | --- |
| `required` | 每个入选回合都必须有通过当前门禁的慢回放。请求失败、边界未确认或没有合格动作，都停止渲染并保存原因；重跑继续利用有效进度。 |
| `auto` | 配置模型后执行核验，未通过的回合可省略慢放，完整回合仍保留。因此该模式不承诺每球都有慢回放。 |
| `off` | 关闭自动核验，使用有效既有记录或本地动作候选；本地候选不是已完成的视觉核验。 |

`--ranker rules` 配合默认 `auto` 不调用模型；显式指定 `required` 才独立启用回放核验。`auto` 缺少模型或密钥时记录 `unavailable`，保留本地候选行为。趣味榜使用自己的完整短事件规则。

## 如何减少错选和截断

程序先通看整个入选回合，再比较其中的动作候选。所有进入候选名单的动作都会继续检查，困难救球可以胜过普通进攻；不会因为前面一个动作已获批准就直接结束比较。更有潜力的候选置信度不足时，保留为未解决，不能直接丢弃后退回普通进攻。潜力比较同时参考粗看和后续连续画面提出的动作类别、精彩度；这些未确认的判断只用于阻止过早批准，不能作为通过依据。

每个候选先做连续画面复核，再交给独立的一轮核验。后一轮只收到焦点时间和画面，不收到上一轮的动作类别、评分、理由或所选首尾。同一次触球在两轮中被分别判断成救球和扣球时，先保留为未解决，防止采用错误动作类别对应的较短结尾。它必须重新观察主触球，以及触球后的实际处理：进攻后要看见对方接应或球死，救球后要看见队友重新组织回球、对方接应或球死。普通跳传不能因为起跳就当作扣球，空中球的自然最高点也不能当作下一次触球。

输入保留逐帧全景，并提供按时间排列的概览。能取得可靠空间提示时，触球附近优先提供连续的原分辨率细节，便于对照触球前、中、后的手臂与球路。全景和细节使用同一个实际原片时间戳，不制造中间帧，也不以局部裁图代替完整球路。

模型用本轮真实帧号指出准备、触球和后续事件。程序可从**已经提供给该轮核验的实际帧**中向两侧增加播放余量，保留原有动作与事件锚点；不会凭公式推算一个未看过的结尾。如果开头已在动作中、尾部必要处理尚未结束，仍须重新选择锚点或扩窗核验。扩窗不会超过入选回合范围。

球轨迹提供额外的截断检查：例如模型称救球完整，但轨迹显示下一次明显触球仍在所选结尾之后，就要求继续复核。轨迹缺失或没有发现冲突，都不能单独证明动作完整。

`required` 的全覆盖要求会在渲染时再次检查，不能通过直接调用渲染器绕过。它保证流程要求得到执行；模型事实判断是否正确，还需看真实画面。

## 恢复与来源核对

`replay_reviews.json` 保存逐球结果及原因，绑定原片清单与剪辑单。渲染还会核对原片内容、球轨迹、核验策略和实际证据产物；这些内容改变后，旧的自动批准不能直接套用。已绑定原片的人工或助手视觉复核记录可以保留；旧版自动记录必须经过当前门禁。

成功的单次视觉请求可以复用。仅增加扩窗次数等流程预算，不必重新支付相同问题的调用；更换原片、模型、问题、采样参数或相关视觉协议时会重新请求。回合最终结果另行绑定完整核验策略和轨迹。密钥不写入提示词、日志或缓存。

`--replace-replay-reviews` 可将既有逐球记录重新交给自动流程，有效请求缓存仍可复用。

## 当前验证范围与限制

模型曾在真实片段中误判动作类型和后续处理，流程批准不能保证慢放窗口完整。独立核验、连续细节和轨迹检查用于阻断已知错误；发布前仍应查看成片的动作与结尾。

离线测试覆盖协议、缓存绑定、候选选择和渲染校验；解码、帧数及原片画音对齐不能替代真实比赛的内容检查。历史逐次请求、私人录像验收和实验成片仅保存在本地，不随源码分发。
